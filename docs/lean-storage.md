# Local lean storage migration
Schema 6 preserves contract-5 requests and current records. Existing schema-5 databases remain supported; old schema-5-only binaries deliberately refuse schema 6.
Historical receipt IDs remain fenced. Existing accepted requests are never treated as new work if cold data is unavailable. One explicitly authorized corrupt receipt is retired with a visible no-replay fence. Other historical bytes remain in the verified compressed archive.
New receipts use lossless compressed JSON storage. Ordinary current-record reads and writes need no cold restore. Exact historical receipt/history/export access requires an explicit bounded restore; historical free-text search refuses incomplete physical-field results. Full diagnostics report incomplete when cold data is unavailable; quick checks do not certify historical health.
The archive manifest path is stored in receipt catalog entries. Keep it and its compressed archive. Run tools/restore-archive.py with --manifest, --target <manifest-directory>/archive-cache/restored.db, --max-bytes, --reserve-bytes and --explicit-restore only when historical access is required. Restore verifies full compressed and decoded hashes and identity, never restores automatically, and retains interrupted partials for reconciliation. Original archive corruption may still prevent specific historical reads; it is not hidden.
The migration preserves instance, epoch, latest revision, all current records and associations. The source database is retained as a rollback file until separately authorized cleanup. After new writes, rollback requires reconciling those writes; do not blindly swap back.

## Bounded diagnostic reports
Doctor still validates the complete selected scope. Reports bound ordinary issue samples to 128 KiB, individual details to 8 KiB, and large decision/handoff ID lists to 8 KiB each; the JSON data report stays below 256 KiB. `reporting.issue_count` and `issue_counts` count every finding, including grouped cold receipts. `issues_omitted` counts unsampled ordinary issues; the cold summary separately reports omitted receipt IDs. `reporting.lists` gives exact total/returned/omitted counts, and `fields_truncated`/`issue_details_truncated` disclose clipped details. Health and completeness use all findings, never just samples. Ordinary small reports preserve their existing values. This bounds report serialization, not the work or memory required for exhaustive SQLite/semantic validation. Human pretty-printing and the outer response envelope add overhead.

Existing `--quick` schema/metadata checks remain explicitly incomplete and cannot replace full validation. No timeout budget was increased by this hardening.

## Cache verification and interrupted publication
The explicit restore publishes a verified cache identity (size, modification time and file ID) with its checksum receipt. Readers check that identity before and after reading; a changed cache or older receipt without identity fails closed with `archive_restore_required`. These local generation checks detect ordinary mutation/replacement, not malicious privileged timestamp/file-ID forgery. They do not silently hash or restore a multi-gigabyte archive during a read.

If a completed cache exists after interrupted receipt publication, run the same explicit restore command with `--verify-existing` and an adequate `--max-bytes`. It rehashes the existing target and checks metadata under the time budget, then atomically publishes its receipt, without decompressing again or overwriting database bytes. A mismatched target or different pending receipt remains untouched. A normal restore publishes its target exclusively; it cannot overwrite a competing target. Temporary partials from an interrupted restore remain for reconciliation. This is an opt-in recovery operation, not an automatic retry or request replay.
