# Lodestar 1.0.1 zero-touch first-run codeplan

Date: 2026-07-31

Branch: `zero-touch-setup`

Baseline: `dbd32d9`

## Objective

Remove the mandatory first-run setup ritual without weakening Lodestar's
machine-first or durability contracts.

A user or agent must be able to make the first valid `put` against an absent
default or explicit database. Lodestar will reserve the destination, create the
five-table schema, and then persist the record. `lodestar init` remains an
optional, idempotent command for callers that deliberately want an empty
registry or the bootstrap response.

## Behavior contract

- A valid `put` initializes an absent or zero-byte destination before writing.
- The initialization path reuses the existing exclusive reservation and
  concurrency behavior; it does not add another lock or storage mechanism.
- First-use contention is bounded. A writer that cannot proceed inside the
  existing busy window reports `database_busy` for an explicit caller retry.
- Invalid JSON or invalid record input does not create a database.
- An existing non-Lodestar file or incompatible database is never replaced.
- Concurrent first writes cannot delete or overwrite the winning database.
- `get`, `find`, `links`, `doctor`, and `export` remain read-only and never
  create a missing database or SQLite sidecar.
- `delete` does not create an empty database merely to report a missing record.
- `import` retains its existing one-step destination initialization.
- Help and version paths remain side-effect free.
- No install script, background process, provider integration, automatic
  export, or second persistence format is introduced.

## Implementation

1. Add one database helper that opens an existing Lodestar database or invokes
   the existing initializer before opening it for a write.
2. Bound observation of an overlapping initializer to the existing five-second
   busy window while its atomic schema transaction becomes visible. Do not add
   lock ownership, stale-lock recovery, or another persistence mechanism.
3. Route only `put` through that helper.
4. Keep parsing and record validation ahead of initialization where possible so
   malformed input remains side-effect free.
5. Update the bootstrap and documentation to say that the first valid write
   creates the database automatically and that `init`, `doctor`, and `export`
   are optional operational commands.
6. Release the patch as `lodestar-agent-context@1.0.1`.

## Verification

- failing-before and passing-after CLI test for first-write initialization;
- invalid-input test proving no database is created;
- existing-file test proving no replacement;
- deterministic modest-burst competing-process regression plus a 320-write
  Linux stress pass proving first-write reservation losers survive inside the
  documented busy window;
- read-only missing-database and help byte/path checks;
- complete unit suite, coverage, package manifest, deterministic pack, and
  installed-artifact smoke;
- hosted Linux, macOS, Windows, and CodeQL checks;
- public npm and GitHub artifact verification after publication.

## Explicit non-scope

- populating knowledge by scanning a repository;
- silently treating an absent registry as complete or known empty;
- running `doctor` on every command;
- automatic exports or backup generations;
- npm post-install writes;
- agent-specific installers or orchestration.
