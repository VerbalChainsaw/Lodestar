# Lodestar v0.5 Project Readiness Implementation

**Date:** 2026-07-30  
**Status:** Accepted for implementation  
**Decision profile:** Forensic  
**Scope:** Lean project-portfolio consolidation and context readiness

## Objective

Make Lodestar the canonical, agent-facing project registry without turning it
into a database, document warehouse, daemon, or general search engine.

Version 0.5 will:

- merge an existing JSON project registry without replacing Lodestar state;
- preserve stable Lodestar project IDs across repeat imports and project moves;
- retain bounded project facts such as descriptions, lifecycle state, commands,
  entrypoints, endpoints, and memory anchors;
- expose those facts through compact linked records rather than the startup
  packet;
- report whether each reachable project has sufficiently complete and fresh
  context;
- preserve the current deterministic JSON/JSONL store, atomic generation
  writer, sidecar indexes, and 16 KiB startup budget.

The external SQL/JSON project list becomes a migration source. It is not a
second runtime authority.

## Hard constraints

- Zero runtime dependencies.
- No SQLite, server, daemon, watcher, embeddings, or vector index.
- No unbounded filesystem discovery.
- No repository content ingestion during registry import.
- No deletion or replacement during the default import path.
- No silent field loss: supported fields are imported and unsupported fields
  produce an actionable validation error.
- No guessed project match when identity is ambiguous.
- No regression to Windows, WSL, Linux, or macOS path handling.
- Existing commands remain available.

## Mechanisms considered

Scoring axes were frozen before implementation:

| Axis | Weight | Type |
|---|---:|---|
| Architecture fit | 3 | quality |
| Data integrity and migration safety | 3 | risk |
| Lean runtime and startup behavior | 3 | quality |
| Verifiability | 2 | quality |
| Implementation complexity | 1 | convenience |

### V1: Catalog merge with inline metadata

Put all imported project fields directly on catalog entries and make the
existing importer merge-aware.

- Score: 42/60 (0.700)
- Advantage: smallest implementation.
- Rejected because it expands the always-read catalog and mixes routing
  identity with optional agent knowledge.

### V2: Linked portfolio records with transactional merge

Keep compact project routing fields in the catalog. Store optional project
knowledge in deterministic linked records owned by the importer. Add one
compact startup card that routes to the wider facts.

- Score: 58/60 (0.967)
- Selected because it preserves the startup contract, existing indexes,
  transaction boundary, and stable IDs while adding useful data width.

### V3: Live SQL/JSON adapter

Read or synchronize an external database at runtime.

- Disqualified before scoring because it introduces parallel authority,
  operational coupling, and a persistence subsystem outside the MVP contract.

## Selected design

### Import identity

For each incoming registry project:

1. Match a prior import key when present.
2. Otherwise match exactly one normalized root.
3. Otherwise match exactly one normalized name or alias.
4. If multiple existing projects match, stop with an explicit conflict.
5. If none match, create one immutable Lodestar project ID.

Repeat imports update the matched project and never change its Lodestar ID.
Projects absent from a later registry remain untouched. `--force` retains the
legacy deliberate-replacement behavior for compatibility, while the default is
safe merge. `--dry-run` executes the same validation and planning without
promoting a generation.

### Imported record shape

Each imported project may have:

- `<project-id>:portfolio`: compact identity and description card;
- `<project-id>:portfolio:operations`: commands, entrypoints, and endpoints;
- `<project-id>:portfolio:memory`: bounded memory anchors and durable status.

The portfolio card is startup-visible. Detail records use `startup: false` and
are reached with `get` or `resolve`. Records carry importer ownership,
provenance, a source key, and a verification timestamp. Re-import replaces only
records owned by this importer and preserves curated, generated, and unrelated
records.

### Supported source fields

The v0.5 adapter accepts:

- `name`, `aliases`, `path`, `repo_path`, `alt_paths`, `roots`;
- `description`, `status`, `activity_summary`, `is_git_repo`;
- `stack`, `test_cmd`, `build_cmd`, `typecheck_cmd`, `test`, `build`,
  `typecheck`;
- `entry_points`, `entrypoints`, `endpoints`, `memory_anchors`.

Values are type checked and bounded. Unknown project fields fail validation so
the importer never silently discards source data.

### Readiness and freshness

`agentctx coverage` continues to report the ten context categories. Version
0.5 adds:

- a per-project readiness state: `ready`, `incomplete`, `stale`, or `blocked`;
- stale and unverified categories for importer/generated records;
- a configurable maximum verification age;
- `--require-ready` for CI or release gates.

Curated records remain durable unless explicitly modeled otherwise. Generated
and imported coverage must have a valid verification timestamp. `doctor`
surfaces incomplete or stale project context as actionable warnings without
making a structurally healthy store unusable.

## Implementation sequence

1. Add bounded registry parsing, identity matching, preview planning, merge
   promotion, and importer-owned linked records.
2. Wire `migrate-projects --dry-run` through the universal CLI.
3. Add freshness-aware coverage and `coverage --require-ready`.
4. Add doctor warnings for incomplete and stale reachable projects.
5. Add migration tests for new, matched, repeated, ambiguous, unsupported, dry
   run, forced replacement, record preservation, and widened fields.
6. Add coverage tests for ready, incomplete, stale, unverified, blocked, and
   command exit behavior.
7. Update package version, README, changelog, release notes, and package
   contents.
8. Run the complete test suite, pack/install smoke tests, Windows and WSL CLI
   checks, material-lift gates, and the same performance suite captured before
   the change.

## Proof contract

The release candidate is acceptable only if:

- all tests pass;
- a packed tarball installs into an isolated prefix;
- the installed CLI initializes, imports, starts, resolves, reports coverage,
  and passes doctor;
- default import is idempotent and byte-identical on the second run;
- no curated or generated record is lost during merge;
- startup remains under the fixed 16 KiB budget;
- deterministic material-lift fixtures still pass;
- before/after performance shows no material regression in `start`, `get`,
  `resolve`, or indexed `find`;
- both WSL and native Windows can execute the packaged CLI.

Performance results will be published honestly, including neutral or losing
microbenchmarks where repository scale is too small for Lodestar to provide a
speed advantage.
