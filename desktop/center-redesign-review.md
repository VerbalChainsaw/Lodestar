## Actionable findings, ranked

1. **MEDIUM, high confidence — C3 retention limits fail across Loader processes.** `DiagnosticLog.cs:30,65,97-120` uses a process-local static `Gate`; the owned-file scan, eviction, and move are not one cross-process critical section. E1 **runtime**: `dotnet run --project work/center-review/DiagnosticRace.csproj --no-restore -- work/center-review/output-current` (exit 0) started 12 processes per round against one disposable root with `maxFiles=1`, `maxTotalBytes=2048`. Five rounds retained **6, 9, 9, 3, 2** valid owned events; two retained **2,997 bytes**. This proves the configured count and byte caps are not invariant under this reachable multi-process scenario; extrapolation to the default 32/262,144 cap is source-based, not separately measured. Some competing writes returned `Failed` without changing the original exception path. Existing `DiagnosticChecks.cs:132-152` only fans out tasks in one process, so its static-lock pass does not falsify this finding. **Minimal repair:** serialize scan/evict/write between processes for the same canonical root (or an equivalent atomic bounded retention protocol), preserving exact-owned-file checks and failure-subordinate behavior. **Falsifier/pass:** the same multi-process fixture always ends within both configured bounds, each retained file parses and contains no sensitive marker, and unrelated files survive.

2. **MEDIUM, high confidence — C5 a successful update blocks the next update.** `BundleTools.psm1:153-157` refuses any existing `Previous`; `:230-239` moves old target to `Previous` but deletes the journal after validating the new target. `Invoke-BundleRecover` and `Invoke-BundleDiscardStage` both require that journal (`:258-301`). E2 **runtime**: `pwsh -NoProfile -File work/center-review/BundleRepeat.ps1` (exit 0) used a fake CLI and disposable database file. First replacement validated the new target, retained the old bundle, and removed the journal; the next `New-BundleTransaction` threw `Existing transaction artifact requires review: ...delivery.lodestar-previous`. No live DB or installed bundle was touched. `Test-BundleUpdate.ps1:67-74` asserts one successful replacement and retained previous, but has no second-update case. **Minimal repair:** define a bounded, explicit lifecycle for the owned previous bundle after successful validation so a second staged update can begin, while retaining a recoverable validated old/new state at every interruption point and refusing ambiguous/unowned paths. **Falsifier/pass:** two consecutive disposable updates succeed; injected failures around both swaps preserve config bytes, unrelated files, and a validated active or recoverable bundle. Do not simply delete an unverified backup to turn this test green.

3. **LOW, high confidence (source-proven) — C1 “Rows scanned” undercounts failed normalization rows.** `LodestarService.cs:424-443` counts `record_errors` against the page budget, while `:336-339` sets `LoadedCount` from successfully projected catalog/current records only; `LodestarHealth.cs:30-32` labels that value “Rows scanned.” `src/queries.mjs:61-73,166-169` shows each selected row becomes either a normalized record or a `record_error`. Thus, with one good and one rejected selected row, the scan examines two and health reports one. No disposable malformed-store run was performed; this is a source-path finding, and the incomplete/error issue is separately surfaced. `OperatorReadoutChecks.cs` tests the catalog/current distinction but not rejected-row semantics. **Minimal repair:** label `LoadedCount` as successfully normalized rows, or carry a separate actual scanned-row count; keep “Current records” distinct. **Falsifier/pass:** a fixture with a rejected row reports both quantities truthfully and retains the issue.
