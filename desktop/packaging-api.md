## Commands and behavior

From the repository root, run `pwsh -NoProfile -File .\desktop\scripts\Build-Portable.ps1 -Destination "<absolute-bundle-path>"`. This builds a framework-dependent Windows WPF runtime using installed reference packs and an empty local NuGet feed. It runs `npm pack --json --ignore-scripts --offline` from current source with a transaction-local cache. `Destination` is always explicit. For an existing target, omit `NodePath` and `DatabasePath`: the exact existing `interfaces.json` bytes are retained, and passing either override is rejected. A new target requires `-NodePath "<absolute-existing-node.exe>" -DatabasePath "<absolute-existing-db>"`. `-SourceRoot "<repo>"` is optional; the default is two levels above the script. Git provides the current commit and dirty indicator for the manifest. No setup, network feed, install, service, or DB mutation is part of this command. Exit code 0 means the final target passed validation; a failure returns nonzero and reports its exact journal path.

Use `pwsh -NoProfile -File .\desktop\scripts\Build-Portable.ps1 -Destination "<absolute-bundle-path>" -Mode Validate` for a read-only manifest, complete inventory, config-path and local CLI-help check. Use `-Mode Recover` with the same destination after an interrupted swap. It reads only the exact transaction journal and sibling paths: if the old bundle was moved away, it restores that validated bundle; if both target and previous are valid after the new move, it accepts the new target, retains previous, and seals a completed journal. A pre-swap stage remains available for review. During an interrupted previous-retirement operation, `Recover` finishes deletion only of unchanged recorded files and empty directories while a validated target remains active. Use `-Mode DiscardStage` only after reviewing an abandoned active pre-swap transaction; it deletes the journal-owned stage when no previous bundle exists and any current target validates. It also supports a failed first build with no target. These modes never kill a process.

The sibling paths are `<Destination>.lodestar-stage`, `<Destination>.lodestar-previous`, and `<Destination>.lodestar-journal.json`, on the same volume. Stage initialization copies the existing directory, including config, docs, evidence, source and unrelated files; it replaces only staged `Lodestar.Loader.exe`, `.dll`, `.pdb`, `.deps.json`, `.runtimeconfig.json` and `core`. Other root files, including similar names and unrelated executables, remain intact. A hash manifest covers every staged Loader runtime file and every core file, with an exact inventory check. An unfamiliar publish output causes a build failure for an explicit inventory decision. The stage is validated before moving either directory. The executable-path process check occurs immediately before the move. Swap order is target to previous, then stage to target. An exception after either move attempts rollback to the old validated bundle. A crash between moves leaves the previous bundle and journal for explicit recovery.

After success, the completed journal stays beside the validated current and previous bundles. It records the target and previous manifest hashes and an exact file/directory inventory for Previous. On the next Build, the script first verifies both bundles and that inventory, checks the exact Loader executable paths, marks the journal `retiring`, then removes only recorded unchanged files and empty directories from Previous. It keeps the validated current target throughout retirement. The new transaction then stages normally; its swap moves that current target to Previous as the new rollback generation. If retirement is interrupted, the `retiring` journal permits resuming with the remaining recorded entries. A changed file, unexpected entry, reparse path, blocked deletion, in-use Loader, stale stage, or journal-less Previous is refused for review; the script does not adopt an arbitrary sibling or delete it recursively. At most one completed previous generation is retained. A legacy Previous left by an older successful script without a journal must be handled explicitly by the operator before another build.

The local CLI help probe is read-only. The configuration is parsed and all configured paths are resolved as they will be after the final rename. Relative paths inside the bundle are mapped to the stage during validation. `interfaces.json`, database contents, source export and user journals are outside the immutable runtime manifest. `-Mode Validate` therefore proves runtime bytes and path resolution, not the correctness of user data or UI behavior.

The process guard enumerates `Lodestar.Loader` processes and compares their exact executable paths with the destination and Previous executables. An unknown path or enumeration error refuses replacement or retirement. There is no process termination. A process starting between that check and a filesystem operation is still a possible race; a move/validation error triggers rollback or leaves the journal and validated bundle for recovery. Do not run the final build while the Loader is open. The deterministic test uses an injected in-use signal; the coordinator will check the actual open-app refusal.

### Manual restoration after a successful update

The previous bundle is deliberately retained as `<Destination>.lodestar-previous` until the next build begins. To restore it manually, close the Loader, run `-Mode Validate` separately on the current destination and the previous sibling, and run `-Mode Recover` to confirm the completed journal reports `new_target_valid`. Verify that the stage is absent. Choose new, explicitly named empty sibling paths for the current bundle and its completed journal. In one PowerShell shell, recheck the exact absolute paths and that neither Loader executable is running, then move the current destination to the new retained bundle, move Previous to Destination, validate the restored Destination, and move the now-stale completed journal to the new retained journal path. Keep both retained artifacts for review. If interrupted between moves, the validated Previous is still available for restoration; if restoration fails, move the retained current bundle back. Do not leave the old completed journal at its default path after manually changing the target/Previous identities, and do not infer ownership of another sibling by its name alone.

Build only after the coordinator's output-document edits settle. The stage copies docs and evidence once at initialization; a concurrent write to those files can otherwise leave a stale copy. The build does not update source exports or delivered documentation on its own.
